# A shoe is a stack, a cut card and a discard pile, used through its own functions

A shoe is a frozen plain object holding three things: `cards`, the stack still in the shoe, top first; `cutCard`, the cut card's position in it, the number of cards above it; and `discardPile`, the cards burned and discarded since the last reshuffle, top first. `shoe(deck, deckCount, { penetration, random })` stacks `deckCount` copies of the deck one on top of another, shuffles them, and puts the cut card at the penetration: a proportion from 0 to 1, 0.75 by default, of the shoe's cards, rounded to the nearest card. Its discard pile starts empty. Cards come out through `drawFromShoe` and `dealFromShoe`, which call `draw` and `deal` on the shoe's cards, move the cut card up by the number of cards taken, and return a frozen object naming each part, as the stack operations do ([ADR 0001](./0001-functional-core-with-a-chain.md)). `burn` moves cards from the top onto the discard pile, moving the cut card up as well, `discard` puts cards that are finished with onto the pile, and `reshuffle(shoe, { penetration, random })` shuffles the pile back in with the cards left in the shoe and puts the cut card back in. Each of those three returns the new shoe. Anything that only reads a shoe's cards or its pile, such as peeking or counting, is a stack operation on `shoe.cards` or `shoe.discardPile`.

```ts no-test
const rules = { random: seededRandom(42) };
const sixDecks = shoe(standard52(), 6, rules);
sixDecks.cutCard; // 234: three quarters of 312 cards
const { hands, shoe: dealt } = dealFromShoe(sixDecks, 3, 2);
dealt.cutCard; // 228
const played = discard(dealt, hands.flat());
played.discardPile.length; // 6
const next = burn(reshuffle(played, rules));
peek(next.discardPile);
```

## Considered options

- **`draw` and `deal` accepting a shoe as well as a stack.** One verb for both, but the result would change shape with the input, since a shoe has to come back where a remainder would. Every other stack operation would face the same question, and most of them, such as cutting, sorting or drawing from the bottom, would break the cut card. Every `draw` user would bundle and read about shoe code they don't use.
- **The cut card as a marker inside the stack.** Closer to the real thing, but the marker isn't a card, so every stack operation would have to skip it, and a stack typed to custom cards couldn't hold it.
- **A class, or a type with a compile-time brand.** A class loses its methods through `structuredClone`, `postMessage` and JSON, as [ADR 0004](./0004-a-stack-is-a-frozen-array-top-first.md) found for stacks. A brand keeps hand-written shoes out, but a hand-written shoe has no trap like a hand-written card, which type-checks and then never matches `===` ([ADR 0002](./0002-cards-are-interned-branded-objects.md)).
- **A `cutCardReached` field.** It reads best, but it's the same fact as `cutCard === 0` stored twice, so every shoe passed in, and every shoe loaded from JSON, would have to be checked for the two agreeing. A field or helper can still be added later in a minor release.
- **`chain(shoe)` from the start.** While drawing and dealing were the only shoe operations, every method of a shoe chain would have split the shoe and ended the chain straight away, and `chain(s).deal(3, 2).value()` would only have been a longer `dealFromShoe(s, 3, 2)`.
- **Tracking the cards dealt out, so `discard` can refuse a card that never left the shoe.** Cards are interned ([ADR 0002](./0002-cards-are-interned-branded-objects.md)), so the check could only be a count of each card. It would catch a hand discarded twice, but it needs another field on every shoe, and every saved shoe, kept up to date by every draw, deal and burn. A shoe missing that field would be read as having nothing out, so a hand-written one couldn't discard anything, and a hand-written or loaded shoe can hold any cards anyway.
- **The penetration stored in the shoe, for `reshuffle` to reuse.** It saves passing it twice, but it's a setting, and settings go in an options object, not in the data ([ADR 0009](./0009-settings-go-in-one-options-object.md)). It would be one more field to carry, check and serialise, and passing the same options object to `shoe` and `reshuffle` does the same job.
- **The discard pile optional in the type, as it is at runtime.** Every reader would need `shoe.discardPile ?? []`. Required, it costs a shoe written by hand in TypeScript one more field.
- **`burn` returning the burned cards, as `drawFromShoe` does.** Burned cards aren't used, by definition, and they're on top of the pile for anyone who wants to look. Returning only the shoe lets a shoe chain carry on from it.

## Consequences

- The cut card is reached once as many cards have been drawn, dealt or burned as sat above it, and `cutCard` stays at 0 from then on. Dealing can go on past it, as a dealer finishes the round in play; only running out of cards stops a draw. A penetration of 0 makes every round the last before a reshuffle, and 1 deals the whole shoe.
- A shoe of one deck, and a shoe from an empty deck, are allowed. An empty shoe has reached its cut card. Only a shoe has a discard pile, so there's no `burn` for stacks, where burning would only be `draw(deck, 1).remainder`: a one-deck game that burns cards, such as hold'em, uses a shoe of one deck.
- How the copies are stacked before the shuffle, and how penetration is rounded, are fixed for 1.x, so a seeded shoe gives the same cards and cut card in every 1.x release ([ADR 0006](./0006-randomness-is-an-injected-source.md)). The cut card's position is `Math.round(penetration × cards)`: a tie, such as half of 3 cards, goes to the later card, and a penetration rounds as the number JavaScript holds, so 0.58 of 25 cards gives 14, because 0.58 is held as a little less than 0.58. For the same reason, so is where burned and discarded cards go, on top of the pile in the order they had in the shoe or were given in, and the order a reshuffle stacks cards in before it shuffles them: the shoe's cards on top of the pile.
- A reshuffle can happen at any time, not only once the cut card is reached, and takes in only the cards left in the shoe and the pile. Cards still in players' hands stay out, so they're discarded first; discarded later, they wait in the pile for the next reshuffle.
- The discard pile is out of play, as a casino's discard tray is: nothing draws from it. A game that draws from a face-up pile, such as rummy, keeps that pile as its own stack. Dealing on from the pile when a shoe runs out partway through a deal is [#80](https://github.com/SimpleProgrammingAU/deckshoes/issues/80).
- `discard` takes any stack of the shoe's kind of card. Discarding a hand twice puts its cards in the pile twice, so the shoe gains cards: only discarding what was taken keeps the count.
- No stack operation takes a shoe, and `chain(shoe)` throws, because a shoe isn't an array. Burning, discarding and reshuffling return a shoe, so a chain for shoes is now worth having ([#77](https://github.com/SimpleProgrammingAU/deckshoes/issues/77)). Until then, `chain(shoe.cards)` works for reading.
- A shoe is checked by its shape wherever it enters the library: `cards` must be an array, `cutCard` an integer from 0 to the number of cards, and `discardPile` an array or missing. So a shoe written by hand, or loaded from JSON ([#30](https://github.com/SimpleProgrammingAU/deckshoes/issues/30)), works the same as one from `shoe()`.
- The discard pile came after shoes first shipped in an alpha, so it's read as empty when it's missing: shoes written by hand and shoes loaded from JSON before then won't have it. The type requires it, so every reader gets a stack, which a prerelease can still ask of a shoe written by hand in TypeScript. After 1.0, a new field has to be optional in the type as well. A shoe function gives back only the fields it knows, so a field of the caller's own, such as an id, isn't carried over. Neither is a newer field when an app has two installs and the older one takes cards from a newer install's shoe, just as two installs' cards aren't `===` ([ADR 0002](./0002-cards-are-interned-branded-objects.md)). Carrying unknown fields over would mean reading every property of the caller's object.
