# A stack is a frozen array, top first

A stack is a `CardStack`: a `readonly` array of cards whose first element is the top. Every stack operation accepts any array of cards, frozen or not, because it never changes its input, and every stack it returns is a plain frozen array, whether on its own or inside a split's named object ([ADR 0001](./0001-functional-core-with-a-chain.md)). So `stack[0]` is the next card drawn, `stack.length` is its size, and a compact string such as `"AS 10H KD"` lists cards top first. Decks, hands and piles are all stacks. Those words name the role a stack plays, so there are no `Deck`, `Hand` or `Pile` types, and every stack operation works on all of them.

## Considered options

- **An opaque deck object.** It could enforce invariants, but it loses `.length`, iteration, array methods and a readable `console.log`. Adding `length` and iteration back still loses `stack[0]`, array methods and `Array.isArray`, and `structuredClone` or `postMessage` gives `{}`, so a stack sent to a worker would lose every card. It would still have to copy the caller's array safely on the way in, so all it would save is the lint rule that keeps stack operations to `copyStack`.
- **The top at the end of the array**, like a `push` and `pop` stack. It reads backwards in logs and text forms, and every operation copies the array anyway.
- **A separate type per role** (`Deck`, `Hand`, `Pile`). Users would need conversions between them, and the API reference would show three names for one thing.
- **The name `CardCollection`.** "Collection" suggests no order, and order is the point of every operation.

## Consequences

- Stack operations are generic over the card type, so custom cards from [#39](https://github.com/SimpleProgrammingAU/deckshoes/issues/39) work with them unchanged. Most never look inside a card: shuffling, drawing, dealing, cutting, inserting, and finding cards with `===`. Sorting and grouping read only a card's rank or suit, and rank and suit orders are generic over the rank and suit types, so they work on any ranked or suited card. Only text formats and presets are typed to standard cards.
- A shoe ([#28](https://github.com/SimpleProgrammingAU/deckshoes/issues/28)) is its own type rather than a stack, because it also carries a cut card.
- Cards drawn or peeked from the bottom stay in stack order, top first: `drawBottom([A, B, C, D], 2)` gives `[C, D]`, while drawing one at a time gives D and then C.
- A stack operation never builds a stack from a caller's array through anything the array can override. It reads cards by index and `length`, and copies through the internal `copyStack`. So it never uses the array's iterator, where one override changes every spread, loop and destructure. It never calls a method that makes a new array, such as `slice()`, which goes through `Symbol.species` and overrides, and never reads the array's own keys, as `Object.values` does, which skips holes. Any of these lets an array throw, lose cards or change their order. A spread is faster for a whole copy of a frozen stack in V8, but counts are checked against `length`, not what the iterator yields, and it copies the whole stack to take one card.
- Lint enforces this in library code, finding a stack by its name: the glossary's word for its role, or `cards`. A stack reached any other way gets past it, whether through an alias, a cast, a generic bound or a collection such as `hands[i]`. This all applies only to the library's own code: users keep every array operation on the stacks deckshoes returns.
- Lint allows the other array methods, such as `at`, `find` and `reduce`, because it can't tell a call that builds a stack from one that only reads, short of rejecting every call. An override of one changes only that method, not every spread, loop and copy, so a stack built through one is left to review. Adding to what lint rejects within the rule above needs no change here, but a restriction the rule doesn't cover, such as rejecting every call to those methods, reopens this decision.
- A hole in a stack reads as `undefined`, and so takes memory. There's no size limit, so copying a sparse array with tens of millions of slots can run the process out of memory.
